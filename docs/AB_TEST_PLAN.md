# План A/B-тестирования моделей прогнозирования дефолта

## 1. Цель теста

Цель A/B-теста — сравнить две версии модели прогнозирования дефолта по кредитной карте и принять решение, стоит ли выкатывать новую модель v2 вместо текущей v1.

- **Группа A / Control** — модель `v1`, LogisticRegression
- **Группа B / Treatment** — модель `v2`, GradientBoostingClassifier

Модель v1 лучше по recall, то есть чаще правильно находит клиентов, которые реально уйдут в дефолт.  
Модель v2 лучше по precision и ROC-AUC, то есть точнее оценивает риск.

---

## 2. Гипотеза

**H0:** модель v2 не улучшает качество скоринга по сравнению с v1.
**H1:** модель v2 улучшает основную ML-метрику и не ухудшает ключевые бизнес-метрики.

---

## 3. Разделение трафика

Трафик делится 50/50:

- группа A → модель v1
- группа B → модель v2

Разделение выполняется детерминированно по `user_id` через hash-функцию.  
Это важно: один и тот же клиент всегда попадает в одну и ту же группу.

В проекте это реализовано в:

```text
src/ab_split.py```

Публичный endpoint для A/B-теста:

```text
POST /predict_ab```

---

## 4. Длительность теста

Ориентировочная схема:

- 2–4 недели — сбор онлайн-предсказаний;
- 30/60/90 дней — ожидание фактического исхода по дефолтам;
- после накопления фактов — статистический анализ.

Так как дефолт является отложенным событием, финальное решение нельзя принимать только по первым онлайн-логам.

---

## 5. Метрики

### Основная ML-метрика

**F1-score для класса default = 1**

Почему F1:
- в задаче есть дисбаланс классов;
- accuracy не подходит, потому что модель “всем не дефолт” уже даст высокую accuracy;
- F1 балансирует precision и recall.

### Дополнительная ML-метрика

**Recall для класса default = 1**

Почему recall:
- пропуск дефолтника — дорогая ошибка для банка;
- false negative означает, что банк может выдать кредит клиенту с высоким риском.

Дополнительно можно смотреть precision, чтобы не отказывать слишком большому числу хороших клиентов.

---

## 6. Бизнес-метрики

### Approval Rate

Доля заявок, которые модель разрешает одобрить.

```text
approval_rate = approved_applications / total_applications ```

Эта метрика нужна, чтобы модель не стала слишком жёсткой и не снизила количество одобренных хороших клиентов.

### Default Rate among Approved

Доля фактических дефолтов среди одобренных заявок.

```text
default_rate = defaults_among_approved / approved_applications ```

Эта метрика показывает реальное качество риск-решений.

### Expected Loss

Ожидаемые потери:

```text
expected_loss = probability_default * exposure * LGD ```

Где:
- `probability_default` — вероятность дефолта;
- `exposure` — сумма риска, например кредитный лимит;
- `LGD` — доля потерь при дефолте.

Важно: для финального A/B-решения нужно сравнивать не только прогнозный expected loss, но и фактические дефолты после созревания данных.

---

## 7. Статистический анализ

### Для долей

Для сравнения долей используется z-test:

- approval rate A vs approval rate B;
- default rate among approved A vs B.

Также строятся 95% доверительные интервалы для разницы долей.

### Для F1-score

Для F1-score используется bootstrap:

1. многократно сэмплируем наблюдения внутри групп A и B;
2. считаем F1 для каждой группы;
3. считаем разницу `F1_B - F1_A`;
4. строим 95% доверительный интервал.

Если доверительный интервал для разницы F1 выше 0, это аргумент в пользу v2.

### Для Expected Loss

Для expected loss per user можно использовать Welch t-test, так как дисперсии в группах могут отличаться.

Из-за тяжёлого хвоста кредитных лимитов дополнительно можно использовать bootstrap CI или Mann-Whitney U test.

---

## 8. Критерий успешности

Модель v2 выкатывается в production, если одновременно выполняются условия:

1. F1-score для класса default у v2 выше, чем у v1.
2. Recall не ухудшается критически.
3. Approval Rate не падает больше чем на 1 процентный пункт.
4. Default Rate among Approved не становится хуже.
5. Expected Loss per user не увеличивается.

Если условия не выполняются, v2 не выкатывается. Возможные действия:
- изменить порог классификации;
- доработать модель;
- собрать больше данных;
- провести повторный тест.

---

## 9. Связь с архитектурой API

A/B-тест встроен в API:

```text
POST /predict_ab ```

Endpoint:
- принимает `user_id` и `features`;
- определяет группу A/B;
- выбирает модель v1 или v2;
- возвращает прогноз;
- пишет событие в JSON-лог.

В лог пишутся:

```text
user_id
model_version
ab_group
prediction
probability_default
request_id
timestamp ```

Эти данные нужны для последующего объединения с банковскими данными о фактическом дефолте.

---

## 10. Риски и ограничения

1. Отложенный таргет 
Факт дефолта становится известен не сразу, поэтому финальная оценка требует времени.

2. Сезонность
Поведение клиентов может меняться по месяцам. Поэтому группы A и B должны тестироваться одновременно.

3. Повторные заявки одного клиента 
Один клиент должен всегда попадать в одну группу. Поэтому сплит делается по `user_id`.

4. Смещение выборки
Нужно проверять, что группы A и B похожи по ключевым признакам: возраст, лимит, история платежей.

---

## 11. Итоговый отчёт

После теста формируется отчёт:

1. период теста;
2. размер групп A и B;
3. F1, Recall, Precision;
4. Approval Rate;
5. Default Rate among Approved;
6. Expected Loss;
7. доверительные интервалы;
8. p-value;
9. решение: выкатывать v2 или нет.

---

## 12. Итог

A/B-тест позволяет сравнить модели не только по ML-метрикам, но и по бизнес-эффекту.

Для задачи кредитного скоринга важно, чтобы новая модель:
- лучше выявляла дефолтников;
- не снижала чрезмерно approval rate;
- не увеличивала ожидаемые финансовые потери.
