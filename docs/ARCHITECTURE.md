# Архитектура сервиса прогнозирования дефолта

## 1. Контекст

Цель проекта — внедрить модель машинного обучения в production-like сервис для прогнозирования дефолта по кредитной карте.

Основной фокус:
- полный цикл ML (обучение → сохранение → инференс);
- API-сервис;
- контейнеризация;
- логирование;
- A/B-тестирование моделей.
---

## 2. Монолит vs микросервисы

### Выбранный подход: монолит

Сервис реализован как единое Flask-приложение, запускаемое через gunicorn внутри Docker-контейнера.

Причины выбора:
- одна бизнес-задача (скоринг дефолта);
- две модели (v1 и v2) можно обслуживать в одном процессе;
- упрощённое развёртывание (один Docker-образ);
- простота тестирования и воспроизводимости.

### Когда нужны микросервисы

Переход к микросервисам оправдан при:
- разделении онлайн-инференса и batch-обработки;
- необходимости отдельного обучения моделей;
- появлении feature store;
- росте нагрузки и разных SLA.

---

## 3. Обработка запроса

Путь запроса `/predict_ab`:

1. Клиент отправляет JSON (user_id + features)
2. Валидация входных данных
3. A/B-сплит по user_id (детерминированный)
4. Выбор модели (v1 или v2)
5. Инференс (`predict_proba`)
6. Логирование события
7. Ответ клиенту

Модели загружаются один раз при старте сервиса и используются для всех запросов.

---

## 4. Gunicorn и NGINX

### Почему Flask dev server нельзя использовать

`flask run` — это development-сервер:
- один процесс;
- не масштабируется;
- не подходит для production-нагрузки.

### Роль gunicorn (или uWSGI)

Gunicorn — WSGI-сервер:
- запускает несколько воркеров;
- обрабатывает параллельные запросы;
- управляет жизненным циклом процессов.

В проекте используется gunicorn как production-сервер.

### Роль NGINX

NGINX используется как reverse proxy перед приложением:

- принимает HTTPS-запросы;
- балансирует нагрузку;
- защищает от перегрузки;
- управляет таймаутами и буферизацией.

Типичная схема:
``` NGINX → gunicorn → Flask ```

В учебном проекте NGINX не разворачивается, но описан как production-практика.

## 5. RabbitMQ (концепция)

Очередь сообщений используется для асинхронной обработки:

Применение:
- batch-скоринг большого количества клиентов;
- асинхронное логирование событий;
- разгрузка API при пиковых нагрузках.

Принцип работы:
- API кладёт задачу в очередь;
- воркеры обрабатывают задачи отдельно.

В проекте RabbitMQ не реализован, но архитектурно предусмотрен.

## 6. Логирование и мониторинг

### Текущая реализация

- формат: JSON
- файл: `logs/predictions.log`
- также вывод в stdout (Docker)

Лог содержит:
- user_id
- model_version
- prediction
- probability
- статус

### Безопасность

Признаки клиента (features) не логируются, так как это чувствительные данные.

### Production-подход

Логи могут собираться через:
``` Docker → Log collector → Elasticsearch → Kibana ```

Мониторинг:
- latency API
- error rate
- распределение предсказаний

---

## 7. ONNX-ML

ONNX — формат для хранения и выполнения моделей независимо от Python.

Преимущества:
- переносимость (Python, C++, Java);
- ускорение инференса;
- независимость от версии sklearn.

Пример конвертации:

```python
from skl2onnx import convert_sklearn
onnx_model = convert_sklearn(pipeline) 
```

Для выполнения используется `onnxruntime`.

В проекте используется joblib, но ONNX описан как улучшение.

## 8. MLOps-инструменты

### DVC

Используется для версионирования данных:
- хранит данные вне Git;
- обеспечивает воспроизводимость экспериментов.

### MLflow

Используется для:
- отслеживания экспериментов;
- хранения метрик;
- управления версиями моделей.

В проекте эти инструменты не реализованы, но описаны как часть production-пайплайна.

---

## 9. Бизнес-метрики

Помимо ML-метрик используются:

- **Approval Rate** — доля одобренных заявок;
- **Expected Loss** — ожидаемые финансовые потери;
- **Default Rate** — доля дефолтов среди одобренных.

Эти метрики позволяют оценить влияние модели на бизнес.

---

## 10. Итог

Выбранная архитектура:
- проста;
- воспроизводима;
- соответствует учебному масштабу;
- расширяема до production-решения.

Сервис реализует полный ML lifecycle и готов к масштабированию при необходимости.
